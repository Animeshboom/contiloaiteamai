# StudioTrack AI — Deployment Plan

Target: a functional prototype at **zero hosting cost**, deployed from GitHub. See `DEPLOYMENT_AUDIT.md` for why the previous deployment failed.

## Architecture

```
                         GitHub (srinivaspatnaik52-svg/StudioTrack-AI, branch main)
                           │ push
          ┌────────────────┼──────────────────────────────┐
          ▼                ▼                              ▼
  GitHub Actions CI   Cloudflare Pages build        Render (waits for CI ✔)
  (tests, migrations,  npm test && npm run build     docker build ./Dockerfile
   docker build)       VITE_API_BASE_URL=<API_URL>   alembic upgrade head → uvicorn
                           │                              │
                           ▼                              ▼
 Browser ──HTTPS──▶ https://<project>.pages.dev     https://<service>.onrender.com
   │   static SPA, SPA fallback, CSP/_headers             FastAPI /api/v1, /api/health
   │                                                      │  CORS: only the Pages origin
   └──── fetch + Authorization: Bearer <JWT> ────────────▶│
                                                          │ TLS (sslmode=require)
                                                          ▼
                                                   Neon Postgres 16 (free)
```

**Principles**
- The browser talks to Cloudflare Pages (static files) and the Render API. **Only the API talks to Postgres.** The database URL exists only in Render's environment.
- The frontend bundle contains exactly one deployment value, `VITE_API_BASE_URL`, which is public by nature. No secrets ever go in `VITE_*`.
- CORS allows only the exact Pages origin (`CORS_ORIGINS`). Preview origins are opt-in via `CORS_ORIGIN_REGEX`.
- Auth uses `Authorization: Bearer`, not cookies, so cross-origin requests need no cookie, SameSite or CSRF configuration. The preflight allows only `Authorization` and `Content-Type`.
- Production and local are separate: production config lives in the Render and Cloudflare dashboards. Local uses `.env` and Docker Compose in development mode. The API **refuses to start** in production with placeholder secrets, a localhost DB or URLs, or missing CORS origins.

## Why direct calls instead of a proxy

Cloudflare Pages `_redirects` can't proxy to another domain. That would need a Pages Function, which adds moving parts and counts against Workers quotas. Direct calls with a strict CORS allow-list are simpler, the API's origin is visible in the bundle (easy to verify), and the CSP `connect-src` allow-lists `*.onrender.com`.

## Preview / staging

- **Cloudflare preview deployments** are built for every non-`main` branch at `https://<hash>.<project>.pages.dev`. By default the API's CORS **blocks** them, so previews can't touch production data. To let previews call the production API, set `CORS_ORIGIN_REGEX=^https://[a-z0-9-]+\.studiotrack-ai\.pages\.dev$` on Render. Previews then share the production database, so use dummy accounts only.
- **Full staging** (optional, still free): create a Neon branch (`staging`) and a second Render service from the same repo on a `staging` branch with its own `DATABASE_URL` and `CORS_ORIGINS`. Not set up now, to keep things simple.

## Migration safety

- Migrations run at container start: `alembic upgrade head` is idempotent and a no-op when already at head.
- CI applies all migrations to an empty Postgres and runs `alembic check`. A model change without a migration fails CI, so it never deploys.
- Policy: migrations must be **additive** (new tables, nullable columns, or columns with server defaults). Never drop or rename in the same release that stops using a column. Never run `alembic downgrade` against production.
- Before a risky migration: create a Neon branch or a restore point first (free, instant). See the guide.

## Order of execution

1. Branch `deploy/cloudflare-render-neon` → push → CI green → merge to `main` (needs your approval)
2. Neon project and connection string (you)
3. Render Blueprint and env vars (you); the API migrates and bootstraps on first start
4. Verify `/api/health`, then login through the API (script)
5. Cloudflare Pages project (you)
6. Set `APP_BASE_URL` and `CORS_ORIGINS` on Render to the real Pages URL
7. Smoke test (GitHub Action) and full workflow test (`scripts/e2e_workflow.py`)
8. Browser test of each role
9. Record results in `DEPLOYMENT_STATUS.md`. Retire the old Vercel project **only with your approval**.
